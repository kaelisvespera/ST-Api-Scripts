# 架构与实现

更新日期：2026-10-31。对应版本 `2.1.1-tt2.4.6`，安装说明见 [README](../README.md)。76 项 Node 回归测试与 2 项 Edge 浏览器测试通过，手机端实际安装及服务商连接仍待用户验证。

## 1. 交付结构

保留原作者发布的压缩构建，通过明确的文本补丁和少量可读源码适配宿主接口。当前交付为原生前端扩展：扩展管理器从 Git 仓库根目录读取 `manifest.json`，加载 `index.js`，再由该模块加载本地 Vue 与 Zod。运行于酒馆主页面，无需酒馆助手 iframe。

`tools/build.cjs` 同时生成原生入口和旧脚本兼容构建。`ST-ApiManager/` 中五个 JSON 的 import 仍固定到 TT2.4.5 历史提交；这些入口不用于新的原生扩展安装。

## 2. 原生启动与宿主接口

`index.js` 先以 ESM 导入本地 Vue 3.5.22 runtime 和 Zod 3.23.8，再运行 `native-bootstrap.js` 与修补后的上游代码。依赖保留为模块内变量，不要求宿主提供 `window.Vue` 或 `window.z`。

在 TT 中，启动等待 `__TAURITAVERN__.ready` 或 `__TAURITAVERN_MAIN_READY__`，再读取存储及公开 context。TT 会在 host ready 后激活扩展，其中部分第三方扩展在 `APP_READY` 之后延迟加载，因此入口不再无条件等待该事件。

原生代码使用 `window.SillyTavern.getContext()` 取得设置、事件总线、Popup、请求头及保存接口，使用当前窗口的 jQuery。构建移除酒馆助手的脚本按钮注册、`getScriptId()` 和整页样式复制，保留 API 连接区、扩展菜单入口及 `/st-api-manager` 命令。

TT 分支通过绑定宿主的 fetch 使用已有 HTTP 桥，不导入 TT 内部模块。普通 ST 的连接函数不会像 TT 一样自动刷新密钥内存状态，因此 native fetch 在 `/api/secrets/write`、`rotate` 成功后，条件加载同一宿主模块 `/scripts/secrets.js` 并等待 `readSecretState()`。此刷新仅用于普通 ST 原生分支，不用于 TT 或旧 iframe。

## 3. 存储与旧配置兼容

运行时保留上游同步 `localStorage` 形状，但只定义模块内适配对象，不替换浏览器的 `window.localStorage`。

| 宿主 | 保存位置 |
| --- | --- |
| TT 2.4 | `extension.store`，namespace `st-api-manager`、key `state`、默认 table `main` |
| 普通 ST | `context.extensionSettings['st-api-manager']`，调用 `saveSettingsDebounced()` |

两者使用同一值结构：

```text
{ version: 1, values: { 逻辑键: 字符串值, ... } }
```

TT namespace 没有自动绑定到仓库名或安装目录。沿用既有 namespace/key，可以原地读取旧脚本的站点、分组、Key 和轮换状态，无需搬移数据。TT 对应文件为 `data_root/_tauritavern/extension-store/st-api-manager/kv/main/state.json`。

主要逻辑键包括配置 `api_configs_manager`、分类及折叠状态、分类切换索引、管理器设置 `stb_api_management_settings`、无效项扫描信息、账户同步元数据 `st_api_manager_sync_metadata_v1` 和密钥绑定 `st_api_manager_tt_secret_bindings_v1`。

首次明确没有扩展存档时，从已知的浏览器键读取旧数据并保留原值。TT 读取异常会停止初始化，避免用空存档覆盖原配置。写入捕获调用时快照并进入串行队列；`flushTauriTavernStorage()` 等待该队列。普通 ST 的队列提交到宿主设置对象后，实际落盘仍由宿主 debounce 保存流程完成。

## 4. 构建流水线

`node tools/build.cjs` 按以下顺序处理：

1. 读取未改动的上游 `src/upstream-index-2.1.1.js`。
2. 替换 Popup、测试消息和 custom 状态请求，限制当前未支持的 SubModel。
3. 应用分组补丁和配置应用流程补丁。
4. 移除上游重复的密钥实现，注入 `tt-secrets.js`；以 `tt-apply-settings.js` 替换 `Ac` 写入逻辑。
5. 从 `manifest.json` 读取版本，移除旧 source map 引用，前置 `tt-bootstrap.js`，生成兼容脚本。
6. 在同一业务代码上替换酒馆助手事件和脚本容器标记、移除脚本按钮及样式复制，前置本地依赖 import 与 `native-bootstrap.js`，生成根 `index.js`。

构建锚点要求目标只出现一次，区段替换也验证边界。`RA`、`ec`、`Ac`、`JA` 等名称需与上游构建匹配。维护源文件和补丁后重建，不直接手改生成文件；升级上游时逐项核对锚点。

## 5. 模型、分组与配置应用

模型条目以 `groupKey` 关联同站点。分组补丁按规范化模型名保留旧模型各自的分类；新增模型进入未分类。“添加配置”对新旧模型取并集，“编辑配置”允许用户主动取消模型。多标签、共享 Key 更新和既有激活状态保留。

`Ac(config, options)` 用于应用按钮和分类切换：

1. 检查公开 context、设置和主 API 控件；先等待选中密钥注册与激活。
2. 写入来源、端点和本来源模型字段，custom 来源指定 `openai_compat`。
3. 同步本来源模型控件；自定义来源同时更新输入框和下拉框，先设置新值再触发 change，避免异步 handler 捕获旧模型。
4. 清空原生 Key 输入框，避免原生连接再次登记同一密钥；必要时将主 API 切换为聊天补全。
5. 有来源控件时触发一次来源 change，否则点击一次原生连接按钮。来源 handler 可能重设模型，因此同步恢复控件和 settings。
6. 调用宿主设置保存，返回本地应用结果。

非 custom 来源不会通过 fallback 写入 custom 或其他来源的模型控件；本来源控件缺失时仍可写入对应设置。模型列表、`#openai_settings` 或网络探测不作为应用前置条件。SELECT 缺少手动模型时补入选项。

`triggerConnect:false` 不触发来源 change 或连接按钮。按钮缺失或禁用时保存配置并提示手动连接。界面“已写入配置”只报告设置写入，原生网络状态与主动检测单独显示。

## 6. 密钥绑定与生成轮换

`tt-secrets.js` 使用宿主 `/api/secrets/read`、`write`、`rotate` 接口。绑定键为 `SHA-256(secretKey + NUL + 规范化密钥)`，值为原生 ID。仅复用本机绑定且仍存在的 ID，或宿主明确返回、与 Key 完全相同的明文值，不把脱敏后缀、标签或导入的旧 ID 当作相同 Key 的证据。

`ec` 为应用配置登记并激活所选 Key；`RA` 为生成轮换登记 Key，并在新增登记后恢复原有活跃 Key。此前没有任何活跃项时，新写入项按宿主原生行为保持活跃。普通 ST 的刷新由原生 bootstrap 的 fetch 适配完成，TT 原生连接自己刷新实际使用的密钥状态。

原生扩展通过 `context.eventSource.makeFirst(context.eventTypes.CHAT_COMPLETION_SETTINGS_READY, listener)` 注册轮换。该事件在请求参数组装后、发送前逐个等待监听器；监听器把登记得到的 `secret_id` 写入本次请求，再保存下一次轮换位置。事件解绑使用 `removeListener`。保留上游的轮换失败提示及继续使用原生当前 Key 的行为。

## 7. 测试消息与显式检测

原生 `ttGenerateRaw` 将上游测试消息转换为宿主 `/api/backends/chat-completions/generate` 请求。字段包括所选来源、模型、消息数组、`secret_id`、`stream:false` 和 `type:'quiet'`，custom 来源附加端点与 OpenAI 兼容格式。响应长度和温度沿用宿主设置。

测试 Key 通过 `ttRegisterSecret(..., false)` 登记，已有活跃 Key 随后恢复。生成请求按明确 ID 选中测试密钥；不会调用普通聊天生成事件，也不会额外推进管理器轮换位置。检查 HTTP 状态及服务端错误后，从 `choices[0].message.content` 读取文本，支持文本数组。

“检测”继续执行主动模型状态请求；“测试消息”执行实际生成请求。二者均与本地“应用配置”分开，不把模型接口可用性当作保存配置的条件。

旧 iframe 兼容构建仍保留酒馆助手的 `generateRaw` 适配，其参数合同与宿主 context 的同名函数不同。

## 8. 验证与发布

本轮最终通过 76 项 Node 回归测试和 2 项 Edge 浏览器测试。覆盖分组、存储迁移、密钥指纹与旧 ID、重复应用、原生请求参数和 native bootstrap；`native-connection.test.cjs` 读取最终构建并运行 TT 原版连接/状态函数。原生 ST 与 TT 密钥刷新差异、异步下拉模型和跨来源控件作为本轮重点回归路径。

真实 Edge 的 `native-extension.browser.cjs` 加载根 manifest、本地依赖和完整生成 bundle，验证无酒馆助手环境下的入口、配置应用、测试消息、轮换、刷新后读取及普通 ST 页面。`iframe-realm.browser.cjs` 保留历史 iframe/代理父窗口兼容检查。测试使用本地宿主和服务端 fixture；尚未验收手机 WebView、用户真实 Key 或真实服务商连接。

```sh
node tools/build.cjs
node --experimental-vm-modules --test tests/*.test.cjs
node --test tests/native-extension.browser.cjs tests/iframe-realm.browser.cjs
```

发布时上传原生根入口、manifest、vendor 及许可证、公开文档、源码、补丁和测试；保留既有远端文件，不提交用户配置、截图、聊天或本地清理归档。发布后读取远端 manifest、入口和依赖并核对内容，记录实际提交 SHA。原生安装跟随仓库分支，不再要求用户修改远程 import。

原生扩展的版本见 manifest；对应发布内容与提交可在仓库历史中核对。历史脚本 JSON 保持 TT2.4.5 固定提交，不改为原生扩展入口。
